This document is the acceptance log for **TASK-053** of the Jarvis Windows port
(v0.4.0). It proves the existing mid-session "model missing" / HF download UX —
already exercised on macOS via `FirstRunDownloadOverlay`, the daemon's
`model_setup` / `model_download` event contract, and Settings → Diagnostics →
re-run setup — behaves the same on a Windows host. No Windows-specific code is
added; this is a verification task.

The macOS v0.3.0 acceptance docs in this directory
(`v0.3.0-overlay-acceptance.md`, `v0.3.0-meeting-mode-acceptance.md`) and the
sibling Windows docs (`v0.4.0-windows-hud-acceptance.md`,
`v0.4.0-windows-friday-pairing-acceptance.md`) are the stylistic templates —
this file mirrors their structure.

This task is **manual** (see Test Coverage Map in
`plans/jarvis-windows-port.md` — "Background HF model download UX on Windows /
TASK-053 / manual"). It must be executed by a release engineer with a Windows
host before tagging v0.4.0. macOS contributors cannot run it locally; this doc
documents the contract that the release engineer must satisfy.

## Architecture under test

```
Python daemon (scripts/jarvis-daemon/)
  +-- model_status.prefetch_models()        emits model_setup{state, models_pending}
  |   +-- snapshot_download (HF Hub)        downloads VibeVoice + Whisper into
  |                                         %USERPROFILE%\.cache\huggingface\hub
  |   +-- _TqdmEmitter                      emits model_download{state, pct, ...}
  |
  +-- WebSocket -> Wails event bridge       app_setup.go::bridge*
                                            forwards model_setup + model_download
                                            to the React HUD as Wails events.

React HUD (frontend/src/)
  +-- FirstRunDownloadOverlay.tsx           full-screen overlay; self-mounts on
  |                                         model_setup{state:downloading},
  |                                         self-unmounts on
  |                                         model_setup{state:ready}.
  |   +-- per-model row                     shows progress, ETA, and on `error`
  |                                         state renders an inline "Retry"
  |                                         button that sends
  |                                         {type:'retry_model_download'} back
  |                                         to the daemon.
  |
  +-- DiagnosticsPanel.tsx                  "Models" row turns red when any
  |                                         model is missing/unloaded; copy/
  |                                         report-bundle includes the model
  |                                         list so support can triage.
  |
  +-- SettingsView -> Diagnostics tab       user-discoverable surface for
  |                                         re-running setup mid-session.
  |
  +-- App.tsx                               calls RunSetup() once on first
                                            launch; SetupScreen renders while
                                            install-daemon.ps1 / .sh runs.
```

The mid-session re-launch path the user takes when a download has failed
silently (e.g. cached partial state, HF servers were down on first launch,
disk full mid-download, user skipped the first-run prompt):

```
Voice action -> daemon raises "model missing" / load error
  -> HUD orb settles in an error state (per OverlayPanel state machine)
  -> User opens Settings -> Diagnostics
     -> "Models" row is RED, raw text lists missing model
     -> Diagnostics actions row exposes a CTA that re-fires RunSetup()
        (or equivalent: "Open setup again" / "Re-run setup")
  -> SetupScreen mounts on top of the HUD; phases 3 + 4 (HF model download)
     re-emit model_setup state=downloading; FirstRunDownloadOverlay would
     also mount if the HUD path was taken first.
  -> On model_setup state=ready, SetupScreen and the overlay both unmount;
     orb returns to idle. No daemon restart required.
```

The Windows-specific concerns this doc validates:

1. The HF Hub cache directory resolves to `%USERPROFILE%\.cache\huggingface\hub`
   on a vanilla Windows install (TASK-017 verified the path; this doc verifies
   the UX consequences when files inside that directory are missing /
   corrupted).
2. WebView2 renders the same React HUD as macOS — no platform-conditional
   styles or layout bugs in the overlay's progress rows on Windows DPI
   scaling (100% / 150% / 200%).
3. The "Re-run setup" CTA inside `DiagnosticsPanel` (and any equivalent
   `SetupScreen` mid-session entry point) is reachable without restarting
   `jarvis.exe`. A daemon restart is acceptable as a fallback as long as it
   does not require the user to kill the process from Task Manager.
4. The retry CTA on a per-model error row (`FirstRunDownloadOverlay`'s
   `onRetry` handler -> `retry_model_download` message) actually retries on
   Windows (no path-separator regression in the daemon's retry handler).
5. The daemon does **not deadlock** when an HF download fails on Windows.
   "Deadlock" here means the daemon process stays alive but stops responding
   to PTT / voice commands until killed. The retry path or a subsequent
   `request_model_setup` must un-stick it.

## HF cache state cheat-sheet (PowerShell)

Use these one-liners to inspect / mutate the cache between scenarios. Run as
the **same user** that runs `jarvis.exe` (the daemon resolves
`%USERPROFILE%` from the daemon process's user, not the elevated admin).

```powershell
# Where the HF Hub puts everything on Windows
$cache = "$env:USERPROFILE\.cache\huggingface\hub"

# 1. List what's on disk
Get-ChildItem $cache -Directory -ErrorAction SilentlyContinue |
  Select-Object Name,
                @{n='SizeMB';e={
                  [math]::Round(((Get-ChildItem $_.FullName -Recurse -File `
                    -ErrorAction SilentlyContinue |
                    Measure-Object Length -Sum).Sum / 1MB), 1)
                }} |
  Format-Table -AutoSize

# 2. Move the whole cache aside (so daemon must re-download)
$ts = Get-Date -Format yyyyMMdd-HHmmss
Move-Item $cache "$cache.bak-$ts" -ErrorAction SilentlyContinue

# 3. Restore (after scenarios, if you want to skip re-download next test)
# Move-Item "$cache.bak-<timestamp>" $cache

# 4. Corrupt a specific model's blob so load fails mid-session
# (Pick a small file under blobs\ and truncate it. Use ONLY for scenario 3.)
$blob = Get-ChildItem "$cache\models--mlx-community--whisper-small.en-mlx\blobs" `
  -File | Select-Object -First 1
Clear-Content $blob.FullName -Force  # empties the file in place
```

## Manual scenarios

### Scenario 1 — First-launch download via SetupScreen (baseline, parity with macOS)

This is the happy path. Confirms the v0.2.x SetupScreen flow that already
ships on macOS works on Windows, since TASK-053's mid-session re-launch
re-uses the same machinery.

- [ ] HF cache is **empty** (run cheat-sheet step 2).
- [ ] Launch `jarvis.exe` for the first time. `SetupScreen` mounts (not the
      HUD orb) because `IsSetupComplete` returns false.
- [ ] Phases 1 + 2 (venv + daemon dependencies via `install-daemon.ps1`) tick
      to green within ~2-5 minutes (network-dependent — first PyTorch wheel
      install dominates).
- [ ] Phase 3 / 4 emit `model_setup state=downloading`. The SetupScreen
      shows per-model rows for VibeVoice + Whisper with progress bars,
      `pct`, ETA, and a tqdm-style throughput readout.
- [ ] Both models complete. `model_setup state=ready` is emitted. SetupScreen
      unmounts; HUD orb takes over and enters idle state.
- [ ] `%USERPROFILE%\.cache\huggingface\hub` now contains
      `models--microsoft--VibeVoice-Realtime-0.5B` and
      `models--mlx-community--whisper-small.en-mlx` (paths match the
      TASK-017 acceptance criteria).
- [ ] Push-to-talk one short utterance (`"hello jarvis"`). The orb cycles
      through listening -> processing -> speaking and the phone (if also
      paired per TASK-016) plays back a reply. This proves the full loop is
      live, not just the download.

### Scenario 2 — Mid-session model-missing trigger (AC #1)

This is the **primary verification** for TASK-053. We forcibly delete the
on-disk models **while the daemon is running** and verify the next voice
action surfaces a clear "Re-run setup" CTA — not a silent gray-out.

Setup:

- [ ] Scenario 1 complete. Models are on disk and the orb is idle.
- [ ] Without quitting `jarvis.exe`, in PowerShell:

      ```powershell
      $cache = "$env:USERPROFILE\.cache\huggingface\hub"
      Move-Item "$cache\models--microsoft--VibeVoice-Realtime-0.5B" "$cache.bak-vibevoice"
      Move-Item "$cache\models--mlx-community--whisper-small.en-mlx" "$cache.bak-whisper"
      ```

Expected user-visible behaviour:

- [ ] Trigger a voice action (PTT, or whatever wake-word path is configured).
- [ ] The daemon attempts to load Whisper / VibeVoice from disk and fails.
      The orb settles into an error / disconnected state (per
      `OverlayPanel`'s state machine) — **not a frozen `listening` state.**
- [ ] Open **Settings -> Diagnostics**. The "Models" status row is RED /
      shows a non-OK badge. The raw value lists at least one model as
      missing or unloaded (`whisper: not loaded` or equivalent).
- [ ] An actionable CTA is reachable from a single screen — either:
  - A "Re-run setup" button on the Diagnostics panel that re-fires
    `RunSetup()` (preferred — matches the macOS pattern), **or**
  - A "Copy report bundle" CTA + a documented next step that points the
    user at "Settings -> Diagnostics -> Re-run setup" (acceptable if the
    button is on a sibling tab as long as the path is one click).
- [ ] Clicking the CTA mounts `SetupScreen` (or an equivalent
      mid-session download overlay) on top of the HUD. Phases 1 + 2 short-
      circuit to green (already installed). Phases 3 + 4 emit
      `model_setup state=downloading` again. The per-model rows reappear.
- [ ] Both models re-download into the original HF cache path. On
      `model_setup state=ready`, the SetupScreen unmounts.
- [ ] PTT a second utterance. Voice loop works end-to-end. **The user did
      not have to quit `jarvis.exe` or kill the daemon from Task Manager.**

Cleanup:

- [ ] Optional: remove the `.bak-vibevoice` / `.bak-whisper` directories you
      created above. Keep them if you want to re-run scenario 2 quickly
      (move them back into place to reset the on-disk state).

### Scenario 3 — Mid-session model load failure (corrupt blob, AC #2: no deadlock)

Variant of scenario 2 that exercises the "model file exists but is
unusable" path — Pipecat raises during the load, not during the download
probe. This is the most likely real-world Windows failure mode (antivirus
quarantines a model blob, disk runs out mid-download, etc.).

Setup:

- [ ] Scenario 1 complete. Models are on disk and the orb is idle.
- [ ] Without quitting `jarvis.exe`, corrupt a Whisper blob:

      ```powershell
      $cache  = "$env:USERPROFILE\.cache\huggingface\hub"
      $blob   = Get-ChildItem "$cache\models--mlx-community--whisper-small.en-mlx\blobs" `
                -File | Select-Object -First 1
      Clear-Content $blob.FullName -Force
      ```

Expected user-visible behaviour:

- [ ] Trigger a voice action. The daemon log
      (`%USERPROFILE%\.jarvis\logs\daemon.log`) shows a Whisper load
      exception. The HUD does **not** silently freeze — within ~5 seconds
      the orb settles into an error / disconnected state.
- [ ] **AC #2 — Doesn't deadlock the daemon.** Verify in PowerShell:

      ```powershell
      Get-Process jarvis,python -ErrorAction SilentlyContinue |
        Select-Object Id, ProcessName, Responding, StartTime
      ```

      `Responding` must be `True` for both processes. If `python.exe` is
      hung (`Responding = False` or CPU pinned at ~100% with no progress),
      file as a TASK-053 regression and link this log.
- [ ] Re-run setup via the Diagnostics CTA (as in scenario 2). The daemon
      re-downloads the corrupted model in place (HF Hub's content-addressed
      blob layout means an emptied blob's SHA no longer matches → it gets
      re-fetched).
- [ ] PTT works again post-re-run. No restart of `jarvis.exe` was required.

### Scenario 4 — Mid-session retry after transient network failure (AC #3)

This is the **HF-servers-down failure case** from the acceptance criteria.
We can't actually take down huggingface.co, but we can simulate by
toggling network adapters mid-download.

Setup:

- [ ] Scenario 1's HF cache is moved aside (cache empty again — cheat-sheet
      step 2).
- [ ] Launch `jarvis.exe`. SetupScreen mounts. Phases 1 + 2 complete. Phase
      3 starts downloading VibeVoice.
- [ ] While the VibeVoice progress bar is between ~10% and ~80%, drop
      network connectivity:

      ```powershell
      # Find the active adapter, disable it.
      Get-NetAdapter | Where-Object Status -eq 'Up'
      Disable-NetAdapter -Name "<adapter name>" -Confirm:$false
      ```

      Wait ~30 seconds.

Expected user-visible behaviour:

- [ ] The current model's row in `FirstRunDownloadOverlay` (or the
      SetupScreen's equivalent row) transitions to `error` state. An inline
      red banner appears with the daemon's error string and a **Retry**
      button (see `FirstRunDownloadOverlay.tsx` lines ~407-440).
- [ ] **AC #3 — retry CTA appears.** The Retry button is visible, focusable,
      and labeled `Retry` (or equivalent — the bar must show that user
      action is expected, not "please wait").
- [ ] Re-enable the adapter:

      ```powershell
      Enable-NetAdapter -Name "<adapter name>" -Confirm:$false
      Start-Sleep 5
      ```

- [ ] Click **Retry**. The daemon receives `{type:'retry_model_download',
      model:'vibevoice'}` and resumes the download. HF Hub's
      `snapshot_download` resumes from the partial blob — total transfer
      should be less than re-downloading from zero (verifiable by watching
      the throughput; resumed downloads stream the remaining bytes).
- [ ] VibeVoice completes, Whisper completes, `model_setup state=ready`
      fires, SetupScreen unmounts. Orb goes idle.
- [ ] PTT one utterance to confirm the loop works after a resumed download.

### Scenario 5 — Disk-full simulation (defensive, optional)

Useful to catch the "model partially written, daemon reports done but next
load fails" class of bugs. Skip if scenarios 2 + 3 + 4 all pass.

- [ ] Use a small VHD or a USB stick mounted as `Z:\` and redirect the HF
      cache there for one launch:

      ```powershell
      $env:HF_HUB_CACHE = "Z:\hf-hub-cache"
      .\jarvis.exe
      ```

- [ ] Drive runs out of space mid-download. The daemon reports an error.
      The HUD shows the same `error` row + Retry CTA from scenario 4.
- [ ] After freeing space, click Retry. Download completes without manual
      cleanup of orphaned files (HF Hub's `.incomplete` sidecars get
      re-used). If the download cannot recover (the daemon reports a
      file-corruption error that Retry doesn't fix), file as a regression
      and link this log.

### Scenario 6 — Diagnostics report bundle includes model status (sanity)

- [ ] After scenario 2 (or 3), in **Settings -> Diagnostics** click

- [ ] Paste into Notepad. The bundle contains a `- Models: ...` line

- [ ] This is what a user would paste into a GitHub issue / support thread
