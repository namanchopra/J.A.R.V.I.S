This document is the acceptance log for TASK-048 of the Jarvis Windows port (v0.4.0). It
mirrors `docs/v0.3.0-meeting-mode-acceptance.md` (the macOS template) but covers the
Windows surface: WASAPI loopback for system audio (TASK-041 / TASK-042), PyAudio mic
capture on Windows (TASK-043), Start/Stop wiring (TASK-044), and the Windows-specific
Settings → Meeting permission UX (TASK-045).

This task is **runtime-verified on Windows** (release engineer's Windows 10 + Windows
11 boxes). macOS contributors cannot run these scenarios locally; they document the
contract the release engineer must satisfy before tagging v0.4.0.

## Windows-vs-macOS UX baseline

| Surface | macOS (v0.3.0) | Windows (v0.4.0) |
|---|---|---|
| System-audio capture | ScreenCaptureKit (SCK) — Apple's screen + audio capture framework. | WASAPI loopback (`IAudioClient` + `AUDCLNT_STREAMFLAGS_LOOPBACK`) — captures the system mix render endpoint. |
| Screen Recording permission | **Required.** macOS prompts on first use; denial surfaces `ErrPermissionDenied` and the in-overlay "tap to open System Settings" CTA. | **Not required.** Windows does **not** gate system-audio loopback on a Screen Recording permission. There is no Windows prompt for this and no Settings pane to grant it. The Settings → Meeting panel must **not** render a Screen Recording warning row on Windows. |
| Microphone permission | macOS Microphone privacy prompt; CapabilityAccessManager-equivalent. | Windows `Settings → Privacy & security → Microphone` toggle. App-level grant. Status readable via `CapabilityAccessManager` registry under `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\CapabilityAccessManager\ConsentStore\microphone\NonPackaged`. |
| Calendar auto-suggest banner | `HudMeetingBanner` — Google Calendar OAuth, keyword match against `cfg.meetingKeywords`. | Identical code path; only verify the banner renders + START button works on Windows. |
| Notes directory | `~/.jarvis/meetings/` | `%USERPROFILE%\.jarvis\meetings\` |
| Recap TTS | Same Pipecat daemon TTS path. | Same Pipecat daemon TTS path. |
| Empty-meeting stub | `_(no audio captured)_` / `_(no transcript entries)_` | Identical (same `app_meeting.go` code path; only the screencapture backend differs). |

**Key UX deliverable for TASK-045:** the Settings → Meeting panel and the in-overlay
warning row must show **only** the "Microphone access required" message on Windows.
No Screen Recording row. This file's scenarios verify that absence.

- [ ] Windows 10 (1809+) or Windows 11 host, x64 or arm64.

- [ ] `%USERPROFILE%\.jarvis\meetings\` exists and is writable:
      `New-Item -ItemType Directory -Force "$env:USERPROFILE\.jarvis\meetings"`.

      required only for scenario 2.
- [ ] Bindings regenerated (`StartMeeting`, `StopMeeting`, `IsMeetingActive`,

      the WebView2 inspect window and confirm `window.go.main.App.IsMeetingActive`
      is a function.

## Manual scenarios

### Scenario 1 — Manual start/stop (happy path)

- [ ] Launch `jarvis.exe`. Main HUD visible; daemon `connected`.
- [ ] Open the overlay (`Alt + Space` default on Windows; same chord the v0.3.x
      docs documented for macOS `⌥ + Space`).
- [ ] Locate the 5th icon in the control row — red `●` between interrupt (`■`)
      and back-to-main (`⤢`).
- [ ] Click the `●` icon.
  - On Windows the **only** permission probe is microphone. There is no Screen
    Recording prompt. If the mic is already granted (prerequisite step), no
    Windows prompt appears.
  - On grant (or pre-grant): orb gains a red ring; state label reads
    `RECORDING MEETING`; hint line ends with `· REC`.
  - On denial: in-overlay warning row reads `⚠ Microphone access required for
    meeting mode · tap to open Settings`. The warning must **not** mention
    Screen Recording. STOP scenario 1, go to scenario 4 to re-grant, then
    restart scenario 1.
- [ ] Speak a few sentences naturally (~10–15s of speech).
- [ ] Click the `●` icon again (now `■` STOP state).
- [ ] Within 2–3 seconds, hear Jarvis speak a 2-sentence recap.
- [ ] Toast appears: `✓ Notes saved: 2026-XX-XX-HH-MM-<slug>.md`
- [ ] Verify file landed:
      `Get-ChildItem "$env:USERPROFILE\.jarvis\meetings" | Sort-Object LastWriteTime | Select-Object -Last 3`
- [ ] Open the file. Verify it contains: title header, summary section, key
      points, action items (if mentioned), raw transcript with mic-source tags.

**Expected file structure** (identical to macOS):

```
# <Meeting Title>

_Started: 2026-XX-XX HH:MM (TZ) — duration: ~Xm_

## Summary
<2-3 bullet summary>

## Key Points
- <bullet>

## Action Items
- <bullet, or "(none)">

## Recap
<2-sentence prose summary — this is what Jarvis spoke>

## Raw Transcript
[mic] HH:MM:SS — <utterance>
```

### Scenario 2 — Calendar auto-suggest + auto-stop

- [ ] Create a Google Calendar event titled `test sync` starting 2–3 minutes
      from now, duration 1–2 minutes. (Title must contain a word from
      `cfg.meetingKeywords`: `call`, `sync`, `1:1`, `meeting`, `standup`,
      `review`, `interview`.)
- [ ] Within 60–120 seconds, the main HUD shows a top-center banner:
      `⌖ MEETING IN ~XM` + the event title + `[START]` + `[DISMISS]` buttons.
      (Same `HudMeetingBanner` component as macOS.)
- [ ] Click `[START]`. Banner disappears. Meeting begins (red ring on orb,
      RECORDING MEETING label).
- [ ] Speak a few sentences. Wait for the event's scheduled end time.
- [ ] At the end time (or within 30s of it), the meeting auto-stops. Notes
      file lands in `%USERPROFILE%\.jarvis\meetings\`. Recap is spoken.
- [ ] Verify the notes file's `_Started:` timestamp + duration match the
      calendar event window.

**Auto-stop gate:** Auto-stop ONLY fires for banner-started meetings. If you
start a meeting manually via the overlay `●` icon, it never auto-stops at a
calendar-end time — same gate as macOS.

### Scenario 3 — System audio capture (WASAPI loopback)

- [ ] Confirm a default playback device is selected (Settings → System → Sound →
      Output). For laptops with no external audio, the built-in speakers
      count. **WASAPI loopback only captures from the active default render
      endpoint** — if Windows has no output device the loopback stream errors
      on `Start` (verified in scenario 4 of `screencapture_windows_test.go`,
      TASK-049).
- [ ] Open a browser tab with audio (a YouTube news clip, a podcast — clearly
      spoken speech, not music). Pause it.
- [ ] Start a meeting via overlay `●` icon (or HUD chip).
- [ ] Play 10–15 seconds of clearly-spoken audio in the browser.
- [ ] Stop the meeting.
- [ ] Open the markdown file. The Raw Transcript section should contain entries
      tagged `[system]` whose text approximates the played audio.
- [ ] (Both `[mic]` and `[system]` tagged entries can appear if you also spoke
      during capture — both should be present and distinguishable.)
- [ ] Switch the default playback device mid-test on a second run (e.g. plug in
      headphones). The capture loop should re-acquire the new default render
      endpoint within ~2s — verified by TASK-050. The notes file should still
      contain `[system]` entries spanning the device switch.

**Note on the WASAPI vs ScreenCaptureKit difference:** on macOS, SCK captures
the screen-render audio (per-app routing). On Windows, WASAPI loopback captures
the mixed output at the default render endpoint — i.e. anything you hear on
your speakers/headphones. There is no per-app filter. If you do not want a
specific app's audio captured, mute it in `Volume Mixer` before starting the
meeting.

### Scenario 4 — Permission denial path (failure case)

This scenario validates the Windows microphone-only permission flow. There is
no Screen Recording analog to deny.

- [ ] Open `Settings → Privacy & security → Microphone`.
- [ ] Toggle **Microphone access** OFF (machine-wide), OR toggle the per-app
      toggle for `jarvis.exe` (under "Let apps access your microphone" / "Let
      desktop apps access your microphone") OFF.
- [ ] If Jarvis was running, restart it so the next permission probe re-reads
      the registry. (Live-revocation propagation on Windows is best-effort —
      restart is the deterministic path.)
- [ ] In the overlay: click the `●` icon. Observe in-overlay warning row:
      `⚠ Microphone access required for meeting mode · tap to open Settings`.
- [ ] **Verify the warning row does NOT mention Screen Recording.** Capture a
      screenshot if anything other than "Microphone access required" appears —
      that is a TASK-045 regression.
- [ ] Click the warning row. Windows Settings opens to **Privacy & security →
      Microphone**. (On Windows 10 the deeplink is `ms-settings:privacy-microphone`;
      on Windows 11 the same URI route works.)
- [ ] Re-toggle the relevant Microphone access switch ON.
- [ ] Click the `●` icon again. Recording starts cleanly — no leftover error
      state.
- [ ] Open Settings → Meeting tab. Verify:
  - A `Microphone access required` warning row appears mirroring the overlay
    warning (event-driven via `meeting:permission_error`).
  - **No Screen Recording row** is rendered. (The Mac-only "Screen Recording
    permission required" row from `MeetingPanel.tsx` is suppressed under
    `runtime.GOOS === "windows"` — TASK-045.)
  - Re-granting mic clears the warning on the next meeting start.

### Scenario 5 — Empty meeting (failure case)

- [ ] Start a meeting via the overlay `●` icon.
- [ ] Immediately click it again to stop (within 1 second).
- [ ] A markdown file should still be written, with the `(no audio captured)`
      stub. Same `app_meeting.go` path as macOS, so the stub shape is
      identical.
- [ ] Recap line is **NOT** spoken (no recap for empty buffers — verified by
      `test_empty_buffer_stop_skips_llm_call` in the daemon test suite).
- [ ] Toast still appears: `✓ Notes saved: ...`
- [ ] Open the file; verify the stub structure:
      ```
      ## Summary
      _(no audio captured)_
      ## Raw Transcript
      _(no transcript entries)_
      ```
- [ ] **WASAPI corner:** on Windows, an empty-meeting stop with no playback
      activity must NOT surface a WASAPI "no playback device" error to the
      user. If the daemon logs `AUDCLNT_S_BUFFER_EMPTY` warnings while the
      stop path runs, that is normal — the stub file should still be written.

- [ ] After completing scenario 1 (you have at least one saved meeting now),
      open the main HUD.
- [ ] In the right-column calendar panel, locate the `● START MEETING` chip.
      A small `⟳` Replay button is rendered next to it (visible because
      `hasRecapAvailable` flipped true after scenario 1's stop).
- [ ] Click `⟳`. Jarvis re-speaks the cached recap.
- [ ] Settings → Meeting tab → click `OPEN FOLDER ↗`. Explorer opens to

      `list_recent_meetings` and read back filenames + titles.

## Scripted checks (release engineer)

Run from the repo root on a Windows host with Go 1.25 + Node + Wails CLI + a
Python 3.12 venv at `%USERPROFILE%\.jarvis\jarvis-daemon\.venv` (TASK-004).

```powershell
# Go side — build tag matters; the Windows-only WASAPI test must compile.
go build ./...
go test ./internal/screencapture/... -run Windows -v       # WASAPI tests (TASK-049)
go test ./... -race

# Frontend
cd frontend
npx tsc --noEmit
npm run test                                                # vitest
cd ..

# Daemon
cd scripts\jarvis-daemon
.\.venv\Scripts\Activate.ps1
pytest -v
deactivate
cd ..\..
```

Expected:
- Go: all packages pass under `-race`. `screencapture_windows_test.go` runs only
  with the Windows build tag and exercises at least one full WASAPI loopback
  capture cycle.
- Frontend: ≥490 tests pass (same total as macOS post-TASK-045, since the
  Windows branch is a single conditional in `MeetingPanel.tsx`).
- Daemon: ≥113 tests pass (`tests/test_meeting_handlers.py`,
  `tests/test_recall_last_meeting.py`, etc.).
