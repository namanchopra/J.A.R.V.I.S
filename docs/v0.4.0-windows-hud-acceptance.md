This document is the acceptance log for TASK-014 of the Jarvis Windows port (v0.4.0). The
goal is to prove the Wails-built `jarvis.exe` launches a WebView2 window on Windows 10 +
Windows 11, renders the HUD orb, and degrades gracefully when the WebView2 runtime is
missing on the host. The macOS acceptance docs in this directory
(`v0.3.0-overlay-acceptance.md`, `v0.3.0-meeting-mode-acceptance.md`) are the stylistic
templates — this file mirrors their structure for the Windows surface.

This task is runtime-verified on CI (Windows runners) and on a release engineer's
Windows 10 + Windows 11 boxes before tagging a v0.4.0 release. macOS contributors cannot
run these checks locally; they document the contract that the CI workflow
(`.github/workflows/release-windows.yml`, TASK-018) and the release engineer must
satisfy.

## WebView2 runtime baseline

Jarvis on Windows renders the React HUD inside a Microsoft WebView2 control (Edge
Chromium) embedded by Wails v2. This is the same rendering technology Wails uses on
every Windows host — Jarvis does not bundle a custom Chromium fork.

| Constraint | Value | Rationale |
|---|---|---|
| Target runtime | **WebView2 Evergreen** (the auto-updated runtime distributed by Microsoft) | Matches the Wails v2 recommendation; receives security updates automatically; no per-app distribution work. |
| Minimum runtime version | **100.0.x or later** | Aligns with the lowest version that supports the modern `requestStorageAccess`, `BroadcastChannel`, and CSS `:has()` selectors used by the HUD's overlay + settings views. Earlier runtimes render the orb but break parts of Settings. |
| Minimum Windows version | **Windows 10 1809 (build 17763)** | The lowest Windows release Microsoft supports WebView2 on. The Wails NSIS template's `wails.checkArchitecture` macro already rejects older Windows builds (see `build/windows/installer/wails_tools.nsh`). |
| Architecture | amd64 (x64) and arm64 | x64 builds run native on Windows 10/11 x64; arm64 builds run native on Windows 11 ARM (Snapdragon X / WoA). x64 builds also run under x64 emulation on ARM Windows but ship at lower performance. |
| Bootstrap install path | Inno Setup installer (TASK-054, TASK-057) embeds the WebView2 bootstrapper and silently installs it during first-run if the runtime is missing on Windows 10. | Win11 ships WebView2 preinstalled; Win10 1809+ does not (it was added as a separate download in 2020). |

### Inspecting the installed runtime

Three places report the installed Evergreen runtime version:

1. **PowerShell** (admin install, machine-wide):
   ```powershell
   Get-ItemProperty -Path 'HKLM:\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}' `
     -Name pv -ErrorAction SilentlyContinue
   ```
   The `pv` value is the installed version (e.g. `124.0.2478.97`).
2. **PowerShell** (per-user install, fallback used by some sideload scenarios):
   ```powershell
   Get-ItemProperty -Path 'HKCU:\SOFTWARE\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}' `
     -Name pv -ErrorAction SilentlyContinue
   ```
3. **edge://settings/help** in Microsoft Edge — the runtime ships in lockstep with Edge,
   so the Edge "About" page version is a useful proxy.

If no key is present, the runtime is not installed and Jarvis will surface the
Wails-default install prompt (see scenario 4 below).

## Manual scenarios

### Scenario 1 — Cold launch on Windows 11 (WebView2 preinstalled, happy path)

- [ ] Wipe prior state: `Remove-Item -Recurse -Force "$env:LocalAppData\Jarvis\WebView"` (idempotent — ignore "path not found" errors).
- [ ] Double-click `jarvis.exe` from File Explorer.
- [ ] Within 2-3 seconds a window titled **Jarvis** opens with the dark
      `BackgroundColour: {R:2, G:10, B:8, A:1}` background declared in `main.go`.
- [ ] The React HUD renders. The voice orb visualisation is visible and animates
      (idle state). No black square, no "page failed to load" message.
- [ ] Open a Task Manager (Ctrl+Shift+Esc) → **Details** tab and confirm:
  - `jarvis.exe` is running.
  - One or more `msedgewebview2.exe` child processes are running under it
    (WebView2 spawns a small process tree for the renderer / GPU / utility roles).
- [ ] Resize the window from 1440×900 (default) up to fullscreen and back down to
      800×600 (MinWidth/MinHeight from `main.go`). The HUD reflows without dropping
      content or showing white flashes.

### Scenario 2 — Cold launch on Windows 10 (WebView2 preinstalled via Inno Setup)

- [ ] Confirm the host is Windows 10 build 17763 (1809) or newer — `winver` shows it.
- [ ] Confirm WebView2 is installed via the registry check above. (If not, the
      Inno Setup installer from TASK-057 silently installed it during install; this
      scenario validates the post-install state.)
- [ ] Launch `jarvis.exe` from the Start Menu shortcut.
- [ ] HUD renders within 4-5 seconds (Windows 10's WebView2 has slightly higher
      first-launch latency than Windows 11's preinstalled runtime).
- [ ] Voice orb visible, idle animation playing.

### Scenario 3 — 5-minute idle survival (AC #2)

- [ ] From scenario 1's running window, leave the app idle (no clicks, no keyboard
      focus changes, no resizes) for **5 minutes**. A wall clock or a 5-minute kitchen
      timer is sufficient; the host machine must not sleep.
- [ ] After 5 minutes, click anywhere in the HUD.
- [ ] The orb still animates. The Wails IPC bridge still works — clicking any control
      (e.g. Settings nav) navigates correctly.
- [ ] No crash dialog has appeared. `jarvis.exe` and its `msedgewebview2.exe`
      children are still running in Task Manager.
- [ ] **Failure mode to watch for**: WebView2 "process crash" dialogs (the
      `WebView2ProcessCrash` message from the Wails defaults). If one appears,
      capture the message text and a Process Monitor trace; file as a v0.4.0 blocker.

### Scenario 4 — Failure case: WebView2 runtime missing (AC #3)

This scenario validates the graceful-degrade path when the runtime is missing on
Windows 10 (the failure mode the Inno Setup installer is designed to prevent, but
that a portable / unzipped distribution would expose to the user).

- [ ] On a Windows 10 1809+ test VM, confirm WebView2 is **not** installed: both
      registry queries from [Inspecting the installed runtime](#inspecting-the-installed-runtime) return nothing.
- [ ] Skip the Inno Setup installer for this run — copy `jarvis.exe` (and the
      bundled `Resources\` directory once TASK-055 lands) into a folder by hand.
- [ ] Double-click `jarvis.exe`.
- [ ] **Expected** (the Wails v2 default behaviour — see
      `pkg/options/windows/windows.go::DefaultMessages` upstream):
  - A native Windows message box appears titled **Missing Requirements**.
  - The body reads "This application requires the WebView2 runtime. Press OK to
    open the download page. Minimum version required: ..." (the Wails default
    `DownloadPage` message).
  - Two buttons: **OK** and **Cancel**.
- [ ] Click **OK**.
- [ ] The default browser opens to the Microsoft WebView2 download page
      (`https://developer.microsoft.com/en-us/microsoft-edge/webview2/`).
- [ ] `jarvis.exe` exits cleanly (no crash dialog, no zombie process in Task
      Manager). The user can now install WebView2 from the opened page and re-launch
      Jarvis successfully.
- [ ] **Negative test**: click **Cancel** instead. The app exits cleanly without
      opening the browser. Re-launching surfaces the same dialog (i.e. the choice is
      not cached).

### Scenario 5 — Persistent user-data path

- [ ] Confirm `wails.json` declares `windows.webviewUserDataPath` =
      `%LocalAppData%\Jarvis\WebView` (TASK-003). The folder must exist after the
      first launch.
- [ ] Launch `jarvis.exe`, dismiss any onboarding, then close the window.
- [ ] Run in PowerShell:
      `Get-ChildItem "$env:LocalAppData\Jarvis\WebView"`
- [ ] The directory exists and contains `EBWebView\` (the WebView2 user-data shape).
      Cookies, localStorage, and the React HUD's persisted preferences live here —
      not in the legacy `%APPDATA%\jarvis.exe\` path that an unset `webviewUserDataPath`
      would default to.

## Scripted checks (release engineer)

Run from the repo root on a Windows host with Go 1.25 + Node + Wails CLI installed:

```powershell
# Build the Windows binary (amd64 host).
wails build -platform windows/amd64 -clean
# Sanity-check the binary signature (Authenticode, only once TASK-056 lands).
Get-AuthenticodeSignature .\build\bin\jarvis.exe | Format-List Status,SignerCertificate
# Launch and check it reaches Ready within 5s.
Start-Process .\build\bin\jarvis.exe
Start-Sleep -Seconds 5
Get-Process jarvis -ErrorAction SilentlyContinue
Get-Process msedgewebview2 -ErrorAction SilentlyContinue
```

The two `Get-Process` calls must both return a row. If `msedgewebview2` is missing
the WebView2 control never spawned — investigate via `%LocalAppData%\Jarvis\WebView`
and the Windows Event Viewer's **Application** log (filter on `WebView2`).
