This document is the acceptance log for **TASK-039** of the Jarvis Windows port (v0.4.0).
It proves the 15 macOS-prefixed system-control Wails bindings (originally landed under
**TASK-015** for macOS — see `app_macctl.go`) behave identically on Windows now that the
Phase 2 tasks (**TASK-020 → TASK-029** plus **TASK-034**) have rewired each binding to a
Windows-native backend in `internal/syscontrol/*_windows.go`.

The macOS acceptance docs (`v0.3.0-overlay-acceptance.md`,
`v0.4.0-windows-friday-pairing-acceptance.md`,
`v0.4.0-windows-hud-acceptance.md`) are the stylistic templates — this file mirrors their
structure for the Windows system-control surface.

This task is **manual** (see Test Coverage Map in `plans/jarvis-windows-port.md` —
"Phase 2 system control / TASK-039 / manual"). It must be executed by a release engineer
with a Windows host before tagging v0.4.0. macOS contributors cannot run it locally; this
doc documents the contract.

## API stability note — why the bindings stay `Mac*`-prefixed

Each scenario below references the binding name exposed to the frontend and the Python
daemon. **All 15 bindings keep their `Mac` prefix on Windows.** This is intentional and
is called out as an acceptance criterion of TASK-039:

| Binding (Wails / TS / Python tool) | Windows backend (Phase 2 task) |
|---|---|
| `MacOpenApp(name)`               | `internal/syscontrol/appcontroller_windows.go` (TASK-020) |
| `MacQuitApp(name)`               | `internal/syscontrol/appcontroller_windows.go` (TASK-020) |
| `MacFocusWindow(app, title)`     | `internal/syscontrol/appcontroller_windows.go` (TASK-021) |
| `MacSetVolume(pct)`              | `internal/syscontrol/audiocontroller_windows.go` (TASK-022) |
| `MacMute()`                      | `internal/syscontrol/audiocontroller_windows.go` (TASK-022) |
| `MacUnmute()`                    | `internal/syscontrol/audiocontroller_windows.go` (TASK-022) |
| `MacSetBrightness(pct)`          | `internal/syscontrol/displaycontroller_windows.go` (TASK-023) |
| `MacToggleDND()`                 | `internal/syscontrol/displaycontroller_windows.go` (TASK-024) |
| `MacOpenPath(path)`              | `internal/syscontrol/filescontroller_windows.go` (TASK-025) |
| `MacSpotlight(query)`            | `internal/syscontrol/filescontroller_windows.go` (TASK-025) |
| `MacScreenshot(target)`          | `internal/syscontrol/screenshotcontroller_windows.go` (TASK-027) |
| `MacClipboardGet()`              | `internal/syscontrol/clipboardcontroller_windows.go` (TASK-026) |
| `MacClipboardSet(text)`          | `internal/syscontrol/clipboardcontroller_windows.go` (TASK-026) |
| `MacListShortcuts()`             | `internal/syscontrol/shortcuts_windows.go` (TASK-034) |
| `MacRunShortcut(name, input)`    | `internal/syscontrol/shortcuts_windows.go` (TASK-034) |

The Python daemon's tool layer maps snake_case tool names (`mac_open_app`,
`mac_run_shortcut`, …) to camelCase Wails methods (`MacOpenApp`, `MacRunShortcut`, …)
with a deterministic transform. Renaming the bindings on Windows would require either a
parallel tool-name namespace or a runtime platform switch in the daemon — both of which
defeat the goal of keeping the cloud LLM's tool surface identical across hosts. Hence
the binding names are an **API contract** that this acceptance log explicitly verifies
the Windows implementation honours.

The companion TASK-028 (Spotify on Windows — `SpotifySearchAndPlay` / `SpotifyPause` /
`SpotifyResume` / `SpotifySkip` routing through the Web API) and TASK-029
(`LaunchReposInTerminal` on Windows — `wt.exe`-backed) are validated in their own
acceptance scenarios (15 + 16 + 17 below) since they ship in the same Phase 2 cut and
share the system-control surface, but they do not count toward the "15 system-control
tools" headline number — that number is exactly the 15 `Mac*` bindings above.

## Prerequisites

- [ ] Windows 10 1809+ or Windows 11 host, x64 or arm64.
- [ ] `jarvis.exe` from the `release-windows.yml` workflow artifact (TASK-018), OR a
      local `wails build -platform windows/amd64` build at `build\bin\jarvis.exe`.
- [ ] `%USERPROFILE%\.jarvis\` prepared by `install-daemon.ps1` (TASK-004). Run the
      TASK-013 smoke check first to confirm the daemon binds locally.
- [ ] WebView2 runtime installed (validated separately by TASK-014).
- [ ] **Notepad, VSCode (or any second windowed app), Microsoft Edge, and Snipping
      Tool are installed.** These are the canned targets each scenario uses.
- [ ] **An audio output device is present** (built-in speakers, headphones, or a
      Bluetooth set). Scenarios 4–6 need a default playback device to attach to.
- [ ] **An internal display is present** (laptop screen or DDC-capable monitor).
      Scenario 7 requires a `LightSensor.WmiMonitorBrightnessMethods`-compatible
      display; external HDMI monitors are intentionally exercised in scenario 7's
      failure branch.
- [ ] PowerShell execution policy: the default `RemoteSigned` is fine for scenarios
      1–14; **scenario 14 (`MacRunShortcut`)** deliberately tightens it to `Restricted`
      to exercise the execution-policy failure surface.
- [ ] `%USERPROFILE%\.jarvis\powershell-scripts\` exists (created by TASK-034 at
      first launch). Drop the test script `hello.ps1` (provided in the appendix) into
      this folder before starting scenario 13.
- [ ] Spotify Desktop installed AND a Spotify Premium account signed into the Web
      Player on the same host (TASK-028 routes through the Web API and requires an
      active device for playback control). Required only for scenarios 15.x.
- [ ] Windows Terminal (`wt.exe`) installed via the Microsoft Store. The fallback to
      `cmd.exe` is exercised by scenario 17.

> **All scenarios below assume `jarvis.exe` is running and reached the `connected`
> daemon state.** Open the HUD's developer console (`Ctrl+Shift+I` on Windows opens the
> WebView2 devtools) and run each scenario by typing the binding call into the console,
> e.g. `await window.go.main.App.MacOpenApp("notepad")`. The console output is the
> ground truth for pass/fail.

## Manual scenarios — happy paths (12)

### Scenario 1 — `MacOpenApp("notepad")` launches Notepad (TASK-020)

- [ ] In the devtools console: `await window.go.main.App.MacOpenApp("notepad")`.
- [ ] Within ~1 s a new **Notepad** window opens with focus. The console call returns
      `""` (empty status string) and the promise resolves (no thrown error).
- [ ] Repeat with `await window.go.main.App.MacOpenApp("notepad.exe")`. Same outcome —
      both the bare exe name and the unqualified app name resolve through
      PowerShell's `Start-Process`.
- [ ] **Keep this Notepad window open** — Scenario 2 closes it.

### Scenario 2 — `MacQuitApp("notepad")` closes Notepad cleanly (TASK-020)

- [ ] With the Notepad window from Scenario 1 still open, run
      `await window.go.main.App.MacQuitApp("notepad")` in the console.
- [ ] Notepad's window closes within ~1 s without a "save changes?" prompt (Notepad
      is empty, so no dirty buffer). The console call resolves to `""`.
- [ ] In Task Manager (`Ctrl+Shift+Esc` → Details tab), no `notepad.exe` process
      remains.

### Scenario 3 — `MacFocusWindow("Code", "")` foregrounds VSCode (TASK-021)

- [ ] Open VSCode (or any second windowed app) and then click on the Jarvis HUD so
      it is the foreground window.
- [ ] In the devtools console:
      `await window.go.main.App.MacFocusWindow("Code", "")`.
- [ ] VSCode comes to the foreground (matches macOS behaviour of `MacFocusWindow`).
      If VSCode was minimised, it is restored first (`ShowWindow(SW_RESTORE)` — see
      TASK-021's AC #2).
- [ ] The console call resolves to `""` (empty status, no error).

### Scenario 4 — `MacSetVolume(50)` sets system volume to 50 % (TASK-022)

- [ ] Note the current system volume (Settings → System → Sound → master slider).
- [ ] In the devtools console: `await window.go.main.App.MacSetVolume(50)`.
- [ ] The Sound panel's master slider updates to 50 ± 1 % (Windows rounds COM
      `IAudioEndpointVolume::SetMasterVolumeLevelScalar` to its internal step).
- [ ] The console call resolves to `""`.
- [ ] Restore the original volume manually (or via `MacSetVolume(<orig>)`).

### Scenario 5 — `MacMute()` mutes the default playback device (TASK-022)

- [ ] System volume is non-zero and audible (play any short audio loop in Edge or
      File Explorer's preview).
- [ ] In the devtools console: `await window.go.main.App.MacMute()`.
- [ ] The system tray volume icon shows the "muted" overlay. Audio stops.
- [ ] The console call resolves to `""`. Calling `MacMute()` a second time is
      idempotent — still resolves to `""`, still muted.

### Scenario 6 — `MacUnmute()` restores playback (TASK-022)

- [ ] Continuing from Scenario 5 (system is muted), run
      `await window.go.main.App.MacUnmute()`.
- [ ] The mute overlay clears. Audio resumes at its pre-mute volume.
- [ ] The console call resolves to `""`. Calling `MacUnmute()` while already unmuted
      is idempotent — resolves to `""`, no state change.

### Scenario 7 — `MacSetBrightness(75)` sets internal display brightness (TASK-023)

- [ ] On a laptop or DDC-capable monitor with WMI brightness support:
      `await window.go.main.App.MacSetBrightness(75)`.
- [ ] The internal display's brightness visibly steps to ~75 %. Open the Windows
      brightness flyout (Action Center → brightness slider) to confirm the slider
      reflects the new value.
- [ ] The console call resolves to `""`.
- [ ] Restore the original brightness manually.

### Scenario 8 — `MacToggleDND()` toggles Focus Assist (TASK-024)

- [ ] Open **Settings → System → Notifications → Focus assist** (Win10) or
      **Settings → System → Focus** (Win11). Note the current state.

- [ ] The Focus assist / Focus state flips (`Off` → `Priority Only` or vice versa).

- [ ] The console call resolves to `""`.
- [ ] Call `MacToggleDND()` a second time to return to the original state.

### Scenario 9 — `MacOpenPath("C:\\Windows\\System32\\drivers\\etc\\hosts")` (TASK-025)

- [ ] In the devtools console:
      `await window.go.main.App.MacOpenPath("C:\\Windows\\System32\\drivers\\etc\\hosts")`.

## Manual scenarios — failure paths (4)

These scenarios deliberately break the environment to validate the error surface. Each
verifies TASK-039's AC #2 ("at least 3 failure scenarios") and the per-task acceptance
criteria for the underlying controllers.

### Scenario F1 — `MacQuitApp("nonexistent-app")` returns a clear error (TASK-020 AC #3)

- [ ] In the devtools console:
      `await window.go.main.App.MacQuitApp("nonexistent-app-xyz123")`.
- [ ] The promise **rejects** with an error whose message contains either
      `"no process matched"` or `"nonexistent-app-xyz123"` (the controller wraps the
      PowerShell exit code into a `QuitApp: %w`-style message).
- [ ] The Jarvis HUD does **not** crash. The next call (e.g. `MacOpenApp("notepad")`)
      still works.

### Scenario F2 — `MacFocusWindow("NoSuchApp", "")` returns a clear error (TASK-021 AC #3)

- [ ] In the devtools console:
      `await window.go.main.App.MacFocusWindow("NoSuchAppNoSuchApp", "")`.
- [ ] The promise **rejects** with an error whose message contains
      `"window not found"` or `"NoSuchAppNoSuchApp"`.
- [ ] The HUD does not crash. The user is not silently left guessing — the rejection
      bubbles to the JS error boundary which surfaces a toast/banner on the
      frontend.

### Scenario F3 — `MacSetBrightness(75)` on an external-only monitor (TASK-023 AC #2)

- [ ] On a desktop with a single external HDMI monitor (no internal display and no
      DDC/WMI brightness support), run
      `await window.go.main.App.MacSetBrightness(75)`.
- [ ] The promise **rejects** with an error message containing
      `"external monitor brightness not supported"` (or close — see
      `internal/syscontrol/displaycontroller_windows.go`'s wording). The brightness
      of the external monitor is **not** changed (Jarvis does not silently no-op).
- [ ] On a *headless* host (RDP into a Windows VM with no console attached), the
      same call rejects with a clean "no display" message and does **not** panic.

### Scenario F4 — `MacRunShortcut("hello", "")` blocked by execution policy (TASK-034 AC #3)

- [ ] In an admin PowerShell, set the policy to `Restricted`:

      ```powershell
      Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy Restricted -Force
      ```

- [ ] In the devtools console: `await window.go.main.App.MacRunShortcut("hello", "")`.
- [ ] The promise **rejects** with an error message that mentions
      **either** `"ExecutionPolicy"` **or** the remediation cmdlet
      `Set-ExecutionPolicy` (TASK-034 AC #3 — surfaces a clear remediation hint).
- [ ] Restore the original policy:

      ```powershell
      Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned -Force
      ```

- [ ] Re-run `MacRunShortcut("hello", "")` — resolves successfully again.

## Companion scenarios — Spotify on Windows (TASK-028)

These four scenarios validate that **all 9 Spotify Wails bindings** route through the
Web API on Windows (no AppleScript fallback). They are listed under the Phase 2
acceptance log because TASK-028 lands in the same Phase 2 cut and shares the
system-control surface, but they are **not** counted in the "15 system-control tools"
headline.

### Scenario 15.1 — `SpotifySearchAndPlay("Bohemian Rhapsody")` (TASK-028 AC #1)

- [ ] Sign in via the Settings → Connections panel (`SpotifySignIn()` → OAuth web
      flow). Confirm `SpotifyIsConnected()` returns `true`.
- [ ] Open the Spotify Desktop client (or the Web Player) and play any track to
      arm the device as the active playback target.
- [ ] In the devtools console:
      `await window.go.main.App.SpotifySearchAndPlay("Bohemian Rhapsody Queen")`.
- [ ] Within ~1 s (Web API latency is ~500 ms vs ~100 ms AppleScript on macOS —
      this is documented in the task), the Spotify client begins playing the
      track. The call resolves to the matched track's Spotify URI.

### Scenario 15.2 — `SpotifyPause()` / `SpotifyResume()` / `SpotifySkip()` (TASK-028 AC #2)

- [ ] Playback in progress from 15.1. Run:
      `await window.go.main.App.SpotifyPause()`. Playback pauses.
- [ ] `await window.go.main.App.SpotifyResume()`. Playback resumes from the same
      timestamp.
- [ ] `await window.go.main.App.SpotifySkip()`. Player advances to the next track
      in the queue.
- [ ] Each call resolves (no error). Latency budget: each within ~1 s.

### Scenario F5 — Spotify failure case: no active device (TASK-028 AC #3)

- [ ] Close Spotify Desktop **and** close any Spotify Web Player browser tab.
      Confirm via `https://api.spotify.com/v1/me/player/devices` (or the Settings
      panel's "active device" row) that no device is active.
- [ ] In the devtools console: `await window.go.main.App.SpotifySearchAndPlay("test")`.
- [ ] The promise **rejects** with an error message that contains
      `"no active Spotify device"` (matches TASK-028 AC #3's exact wording).
      The Jarvis HUD does not crash.

## Companion scenarios — Windows Terminal launch (TASK-029)

### Scenario 16 — `LaunchReposInTerminal([…], "")` opens `wt.exe` tabs (TASK-029 AC #1)

      silently degraded.

## Scripted checks (release engineer)

Run from a Windows host with Jarvis running. These complement the manual scenarios with
quick programmatic sanity checks against the controllers:

```powershell
# 1. Confirm the daemon + Wails process are alive.
Get-Process jarvis -ErrorAction SilentlyContinue | Format-Table Id, ProcessName

# 2. Confirm the Wails bindings file was regenerated.
Test-Path "$PSScriptRoot\..\frontend\wailsjs\go\main\App.d.ts"

# 3. Smoke the PowerShell scripts directory.
Test-Path "$env:USERPROFILE\.jarvis\powershell-scripts"
Get-ChildItem "$env:USERPROFILE\.jarvis\powershell-scripts" -Filter *.ps1 |
  Select-Object Name

# 4. Confirm the screenshots directory was created on first screenshot call.
Test-Path "$env:USERPROFILE\.jarvis\screenshots"
Get-ChildItem "$env:USERPROFILE\.jarvis\screenshots" -Filter *.png |
  Sort-Object LastWriteTime -Descending |
  Select-Object -First 5 Name, LastWriteTime

# 5. Confirm the WMI brightness interface is reachable (Scenario 7's
#    happy-path precondition; will return $null on external-monitor hosts).
Get-WmiObject -Namespace root\WMI -Class WmiMonitorBrightnessMethods |
  Select-Object InstanceName

# 6. Confirm the audio endpoint COM interface enumerates a default device
#    (Scenarios 4-6's precondition).
Add-Type -AssemblyName System.Speech
[Audio]::Devices  # only runs in PS 7+ with the audio module; otherwise
                 # use the Sound Control Panel manually.
```

## Appendix — `hello.ps1` test script (Scenarios 13, 14, F4)

Drop this file at `%USERPROFILE%\.jarvis\powershell-scripts\hello.ps1` before running
Scenarios 14 and 15:

```powershell
# hello.ps1 — Phase 2 acceptance test script for MacRunShortcut on Windows.
# Reads stdin; if empty, prints a fixed greeting. Mirrors the macOS Shortcut
# named "hello" used by TASK-015's acceptance run.
$stdin = [Console]::In.ReadToEnd().Trim()
if ([string]::IsNullOrEmpty($stdin)) {
  Write-Output 'hello from jarvis windows'
} else {
  Write-Output ('hello {0}' -f $stdin)
}
```

For Scenario 14's "second script" branch, drop a `world.ps1` that prints
`world from jarvis windows`. Any script that produces deterministic stdout is fine —
the acceptance is on the binding behaviour, not the script content.
